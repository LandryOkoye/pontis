# Success metrics

How Pontis measures whether it works. Companion to [market-context.md](market-context.md). The metric keys below are the exact `snake_case` names an engineer should implement in the response bodies and the Prometheus exposition.

- **Status:** definitions only. None of the three endpoints exists yet. Nothing here is a measured result.
- **Testnet and synthetic assets only** ([ADR 0014](decisions/0014-scope-expansion-beyond-mvp.md)). Every metric computed from simulated or synthetic data carries `"simulated": true` in the API response and a `simulated` label in Prometheus, so a UI cannot present it as real.
- **Targets are proposals.** The "demo" column is a bar for the scripted testnet demo; the "pilot" column is a bar for a hypothetical pilot with real users that does not exist and is not planned. No external benchmark was used to set them; revise after the first real measurements. Where a number echoes a documented default or a competitor parameter, the row says so.

## Endpoints

| Tag | Endpoint                   | Audience                                                                                                   | Content                                                                                                                                                                            |
| --- | -------------------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P   | `GET /v1/metrics/protocol` | Public, cached                                                                                             | Aggregates only: no account IDs, no quote IDs. One value per key for the windows `24h`, `7d`, `all`                                                                                |
| A   | `GET /v1/admin/metrics`    | Authenticated (admin key, audited like the other admin reads, [ADR 0013](decisions/0013-api-hardening.md)) | Everything in P, plus breakdowns by pair and representation, reasons, and the IDs of open `REQUIRES_RECONCILIATION` quotes                                                         |
| M   | `GET /metrics`             | Operators (Prometheus text format)                                                                         | Counters, gauges and histograms named `pontis_<key>`, with labels `pair`, `representation`, `simulated`. Latency is exported as histograms; p50 and p95 are derived by the scraper |

Conventions: amounts are integer strings in token base units (never floats); ratios are decimals computed from integers and rounded only at output; windows are rolling and anchored on the event time that the "source" column names; every key is documented here and pinned by a unit test when implemented.

## Availability

| Marker                     | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| MVP                        | Computable today from tables already in `packages/db/src/schema/`: `quotes`, `conversions`, `settlement_events`, `indexer_cursor`, `reconciliation_report`, `audit_log` (all in `trading.ts`) and the registry mirror (`asset_representations`, `compatibility_relationships`, `issuers`, `canonical_assets` in `registry.ts`)                                                                                                                                                                                               |
| phase N, not yet available | Needs tables, events or components from a later phase of the plan in [ADR 0014](decisions/0014-scope-expansion-beyond-mvp.md) section 1 and the phase table in the local expansion brief §14. Phase 1: price points, parity deviation points, TVL and volume snapshots. Phase 2: guards and circuit breaker. Phase 3: issuer attestation. Phase 4: reserves. Phase 5: liquidity pools. Phase 6: bridge. Table names for later phases are those in the brief §12.2 where it gives one; otherwise the owning ADR sets the name |

The MVP has no price data, so every USD-denominated metric is a later-phase metric even when the underlying amounts exist today; the MVP versions are reported in base units per representation.

## 1. Conversion health

All from `quotes`, `conversions`, `settlement_events`, `audit_log`: all MVP.

| Key                                                    | Definition                                                                                                                                               | Formula                                                                                                                                                                            | Data source                                                                                                                                                      | Endpoints | Availability | Demo target                            | Pilot target            |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- | ------------ | -------------------------------------- | ----------------------- |
| `conversion_success_rate`                              | Share of conversions that reached the chain and ended `SETTLED`. Quotes that expired or were cancelled never executed and are excluded                   | `count(state='SETTLED') / count(state IN ('SETTLED','FAILED','REQUIRES_RECONCILIATION'))`, over quotes whose `updated_at` is in the window                                         | `quotes.state`, `quotes.updated_at`                                                                                                                              | P, A, M   | MVP          | >= 95%                                 | >= 99.0%                |
| `refund_rate`                                          | Share of on-chain executions that returned the input to the user: refused by the contract (`conversion_rejected`) or payout failed (`conversion_failed`) | `count(event_name IN ('conversion_rejected','conversion_failed')) / count(event_name IN ('conversion_completed','conversion_rejected','conversion_failed'))`, by `block_timestamp` | `settlement_events.event_name`, `settlement_events.block_timestamp`; reason split in A from `settlement_events.data` and `conversions.failure_reason`            | P, A, M   | MVP          | <= 5% (scripted failure runs excluded) | <= 1%                   |
| `requires_reconciliation_rate`                         | Share of executed quotes that entered `REQUIRES_RECONCILIATION` in the window                                                                            | `count(distinct subject, action='quote.requires_reconciliation') / count(quotes in ('SETTLED','FAILED','REQUIRES_RECONCILIATION'))`                                                | `audit_log` (`action = 'quote.requires_reconciliation'`, written by both the indexer and the reconciler), `quotes.state`                                         | P, A, M   | MVP          | <= 2%                                  | <= 0.1%                 |
| `requires_reconciliation_open`                         | Quotes in `REQUIRES_RECONCILIATION` right now                                                                                                            | `count(quotes.state='REQUIRES_RECONCILIATION')`; A also lists the IDs from `reconciliation_report.report.requiresReconciliation`                                                   | `quotes.state`, `reconciliation_report`                                                                                                                          | A, M      | MVP          | 0 at the end of a demo run             | 0 older than 24 h       |
| `requires_reconciliation_mean_time_to_resolve_seconds` | Mean time from entering `REQUIRES_RECONCILIATION` to a terminal state, for quotes that left it                                                           | `avg(resolved_at - entered_at)`; `entered_at` = earliest `audit_log.at` for the quote with that action, `resolved_at` = `quotes.updated_at` once state is `SETTLED` or `FAILED`    | `audit_log.at`, `quotes.updated_at`. There is no transition history table: it is valid because `SETTLED` and `FAILED` are terminal, so `updated_at` stops moving | A, M      | MVP          | <= 15 min                              | <= 4 h (business hours) |

Notes: `refund_rate` counts events, not quotes; an event with no `conversion_id` (the indexer could not link it) still counts. A refund is a correct outcome for a bad request, so a low rate is not a goal for a demo that injects failures; scripted failure scenarios are tagged in phase 9 and excluded from the target. A rising `requires_reconciliation_rate` is the signal that matters, because by [ADR 0012](decisions/0012-reconciliation.md) these are the cases the system could not resolve itself.

## Implementation notes

- **One query module per area,** shared by the three endpoints, so P, A and M cannot disagree. Unit tests pin each formula on fixtures with known answers, including empty windows (a rate with a zero denominator is `null`, not 0).
- **Percentiles** use `percentile_cont` in SQL for JSON bodies; Prometheus gets histogram buckets.
- **Cache:** P is cached for 30 to 60 seconds. A and M are not cached.
- **The chain head** for `indexer_lag_blocks` is an RPC read, so when RPC fails the key is `null` and the endpoint still answers, as `GET /v1/health` does.
- **No hand-entered values.** Every number comes from the database or the indexer; a metric that cannot be computed returns `null` with `"available": false`, not a guess.
- **Targets live in configuration,** not in code, so a pilot sponsor can change them without a release.

References inside tables written as `[S8 in market-context]` and `[S20 in market-context]` point to the numbered sources in [market-context.md](market-context.md).
