# NEP-413 authentication research

- **Verified:** 2026-11-11
- **Status:** Ready for the phase 3 simulated testnet integration
- **Scope:** Wallet login for the issuer portal and role-review API. This is not an on-chain authorization mechanism.

## Sources checked

1. [NEP-413 specification](https://github.com/near/NEPs/blob/master/neps/nep-0413.md), accessed 2026-11-11. The [NEP index](https://near.github.io/NEPs/) lists NEP-413 as Final.
2. [near-api-js signer documentation](https://near.github.io/near-api-js/classes/signers_signer.Signer.html), accessed 2026-11-11. It exposes `signNep413Message` and says verification uses the payload hash.

## Verified facts

- A NEP-413 payload contains `message`, a 32-byte `nonce`, `recipient`, and an optional `callbackUrl`. It is an off-chain wallet signature, not a NEAR transaction.
- The signed bytes are domain-separated by the NEP-413 tag, then Borsh encoded and SHA-256 hashed before the account's ed25519 key signs them. The tag keeps the payload from being interpreted as a transaction.
- The verifier receives the account ID, public key and signature. A Pontis login also has to query the account's access key and require a full-access key. Signature validity alone does not show that the key currently belongs to the claimed account.

## Pontis integration decision

The API creates a one-time, short-lived challenge bound to the API's configured public origin as `recipient`. Its canonical JSON message includes the account, audience, issued and expiry timestamps, the random challenge ID, and an action of `pontis_login_v1`. The API persists the nonce hash and accepts it once.

It reconstructs the exact NEP-413 payload, verifies the ed25519 signature, checks that the public key is a currently installed full-access key through NEAR RPC, then issues a short-lived, account-bound session. It never treats this session as authority to send a chain transaction: privileged endpoints return a wallet-signable transaction and re-check the account's on-chain role when creating that payload.

The local demo uses development accounts and keys only. It is still labelled as testnet authentication, not KYC, identity verification, or proof of any real-world legal authority.

## Implementation checks

- Pin a byte-level NEP-413 verification vector generated by a wallet-compatible implementation.
- Refuse a nonce that is expired, already used, or belongs to another recipient or account.
- Refuse an unknown key and a function-call access key.
- Re-check the access key for sensitive review actions even when the session is valid.
