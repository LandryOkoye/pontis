# Phase 4: custody, reserves and redemption in the indexer, db and scripts

The TypeScript side of [ADR 0020](../decisions/0020-custody-reserves-and-redemption.md) outside the API: mirror tables, event application, the reserve monitor, reconciler rules, and the simulated custodian and back-office. Branch `feat/phase4-indexer`, on `main` (phase 2). The contract is written in parallel; this was built from the ADR and checked against the contract agent's working tree (`pontis-roles`, read only) where files existed. The web app is untouched, and nothing was run against a chain.

## Decisions

- **Replay safety comes from `settlement_events`.** Every event is stored there first; the mirror applier runs only if that insert was new. A start-up rescan of 30 blocks therefore cannot undo a newer custody link or status. Tables that hold one row per event (`reserve_attestations`, `reserve_supply_reads`, `redemption_events`, `redemption_terms`) also carry a unique `(receipt_id, log_index)`.
- **Dirty marks instead of chain reads inside the block transaction.** `custodian_registered` has no name, jurisdiction or evidence, and redemption events change issuer counters the events do not carry. The applier sets `needs_refresh` (or leaves `chain_refreshed_at` older than `changed_at`); `refreshMirrors` reads `get_custodian`, `get_issuer_reliability` and `get_reserve_status` after the pass. A failed read keeps the mark. Unread details are null, never guessed; labels default to `simulated: true`.
- **`reserve_status` keeps event and chain data apart.** The event columns are what `reserve_status_changed` said; `chain_status` is a snapshot of `get_reserve_status`. That is what lets the reconciler tell a breach the indexer has not seen from one it has.
- **`RESERVE_BREACH` is "the contract says breached and the mirror does not", over two runs.** The ADR's phrase "reserve breach not reflected" is read as a database-against-chain check like the vault rules; breaches the mirror already knows are in the monitor report and the audit log. `RESERVE_STALE` is the contract's own `stale` reading (no event exists for time passing); `no_attestation` is not called stale.
- **Escrow is part of what the core accounts for.** For representations with redemption terms or requests, the vault reading's `inventory` includes `get_escrow_ledger.held`, so held escrow is not reported as `VAULT_UNTRACKED_BALANCE`. `ESCROW_MISMATCH` compares the mirror's open escrows (`requested`, `accepted`, `rejected`, `expired`) plus inventory and pending input with the token balance, skips a representation the vault check already flags, and needs two runs.
- **A payload that does not parse is skipped and audited** (`mirror.event_unreadable`), not thrown: a contract/indexer mismatch must be visible without stalling every other event.
- **The monitor is permissionless and optional to sign.** `refresh_supply` and `evaluate_reserve` need no role. With `RESERVE_MONITOR_ACCOUNT_ID` and `RESERVE_MONITOR_PRIVATE_KEY` it signs with near-api-js; without them it only reads and the report says `signer: null`.
- **`GET /v1/admin/reserve-monitor` is not built.** It needs an api-types endpoint and the session and role work; the query is `loadReserveMonitorReport(db)`.
- **Vector.** `test-vectors/reserve-attestation.json` is the contract agent's file, copied byte for byte (their tree, uncommitted at the time). It signs with seed `0xc9..0xe8`, not the `@pontis/dev-keys` reserve-attester seed, and lists six `tampered` cases rather than the ADR's three negatives; the TypeScript test checks each against the valid signature.

## Ambiguities and gaps

- `execute_mint` emits no event in the ADR, so a mint request is `requested` in the mirror until it is minted, failed or cancelled; `minting` is never seen.
- The payloads of `redemption_fulfil_failed` and `redemption_reclaim_failed` are not spelled out; `{id, timestamp_ms}` is assumed. `redemption.rs` was not written when this was done, so the redemption events were read from the ADR only.
- Redemption timeline rows have no transaction hash: receipts do not name their transaction and the hash verifier only knows conversions. The receipt id is the reference.
- An issuer's `controlled_accounts` is set only at `register_issuer`; there is no method to add the back-office account to a seeded issuer (the runbook gives two ways around it).
- `packages/db` declares the enum unions of the new tables locally because `@pontis/domain`'s phase 4 types live on `feat/phase4-api`; after the merge they can import them. The indexer reads the ADR 0020 views through its own `CustodyViews` for the same reason; once near-client has typed wrappers, switch and delete it.
- `openapi.yaml` was regenerated here for the four new kinds, as `feat/phase4-api` regenerates it too: on a conflict, regenerate (`pnpm --filter @pontis/api-types generate`).
- The monitor and the signer cannot be tested against a node here; the signer is a thin near-api-js call and the monitor is tested through a fake.
